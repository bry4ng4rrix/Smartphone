AUDIT DE PARITÉ — pages web (frontend/app/(app)/) vs app Flutter (smartcross/)
=============================================================================

Contexte : audit demandé après découverte en session que le Flutter était
bien plus avancé que prévu (écran Produits/Catalogue complet notamment).
Objectif : photo exacte et actuelle de ce qui existe des deux côtés, page
web par page web, pour décider quoi construire ensuite. Aucune modification
de code effectuée — recherche seule.

Méthode : lecture directe des page.tsx (frontend) et des écrans/providers
Flutter correspondants, plus quelques fichiers backend quand le rôle exact
d'un champ/endpoint n'était pas clair depuis le frontend seul. Le dossier
smartcross/lib/features/catalog/ (catalog_screen.dart, catalog_provider.dart,
catalog_repository.dart, router.dart, nav_items.dart) n'a été QUE lu, pas
modifié — un autre agent le retouche en parallèle de cette session.

Rôles web réels (lib/auth/useCurrentUser.ts:79-95) — à ne pas confondre :
  role backend "admin"    = propriétaire de société (multi-magasins) — noté
                             isSuperAdmin/isAdmin dans le hook (nom trompeur,
                             RIEN À VOIR avec "Label Technology")
  role backend "magasin"  = gérant d'un seul magasin
  role backend "employer" = employé, sous-rôle commande_role PREPARATEUR/LIVREUR
  isGerant = admin OR magasin ; isManager = admin OR magasin (alias identique)
Flutter (core/constants.dart:3) n'a que UserRole{gerant, preparateur, livreur,
unknown} — admin et magasin sont FUSIONNÉS en un seul "gerant" au niveau nav/
routing. La distinction fine admin-vs-magasin existe quand même au niveau
modèle (models/user.dart: rawRole, isCompanyOwner) et n'est utilisée que dans
users_screen.dart. Conséquence notée page par page ci-dessous.

Pattern récurrent (noté ici une fois, pas répété partout) : plusieurs pages
web n'ont PAS de garde au niveau page (pas de "if (!role) return Accès
refusé") — elles sont seulement masquées dans components/layout/sidebar.tsx.
Une navigation URL directe par un rôle non prévu passerait. Pages concernées :
alerts, caisse, movements, reports, suppliers, scanner (scanner n'est même
pas dans le sidebar). Pages AVEC garde explicite ("Accès refusé"/redirect) :
dashboard, pickup, transfers, superadmin, users.

VERDICT : GAP RÉEL, taille moyenne. La caisse "opérationnelle" (ouvrir/
fermer/mouvement du jour) est à parité. Ce qui manque est la vue analytique
transverse (résumé multi-session + catégorisation des dépenses) — utile à
un Gérant qui veut un aperçu financier caisse sans repasser par le web.

4. DASHBOARD — frontend/app/(app)/dashboard/page.tsx (508 lignes)
=============================================================================
RÔLE WEB : garde explicite dashboard/page.tsx:194-208 (if !isGerant → Accès
refusé). Gérant only (admin ou magasin).

ÉQUIVALENT FLUTTER : smartcross/lib/features/dashboard/dashboard_screen.dart
(264 lignes). Route /dashboard réservée à {UserRole.gerant} (nav_items.dart:23).

DÉCOUVERTE IMPORTANTE : les deux dashboards utilisent des ENDPOINTS BACKEND
DIFFÉRENTS. Web appelle GET /users/dashboard/ (users/views.py::DashboardView,
ancien). Flutter appelle GET /api/orders/dashboard/ (orders/dashboard.py::
DashboardView, 196 lignes, docstring "§7.7 Smartreadme.md" — endpoint dédié,
visiblement écrit spécifiquement pour ce dashboard Flutter, scope par
magasins accessibles, filtrable par date_from/date_to). Ce ne sont pas deux
vues du même calcul, ce sont deux calculs distincts.

CE QUE FLUTTER A EN PLUS / MIEUX que le web dashboard :
  - Filtre de période (Jour/Semaine/Mois/Personnalisé, dashboard_provider.
    dart:9-38) piloté au niveau de TOUT le dashboard — le web n'a un tel
    filtre que sur le graphe CA de /reports, pas sur /dashboard.
  - Carte "Analyse financière" complète (dashboard_screen.dart:110-126) :
    CA produits vendus, frais livraison encaissés, total investi
    fournisseurs, bénéfice estimé — calcul du coût de revient réel incluant
    les commandes fournisseurs de la période (orders/dashboard.py:82-92).
  - "Suivi commandes temps réel" par statut (chips, tous les 6 statuts).
  - TOP 20 produits sur 4 dimensions (sous-type/marque/référence/couleur) —
    le web n'a qu'un seul TOP produits (par quantité, tous critères mélangés,
    reports/page.tsx, pas dashboard).
  - Taux de livraison réussie (%), nombre de retours — absents du dashboard web.

NUANCE SUR "PAS DE KPI FINANCIER/IMPAYÉ" (vérification demandée) : c'est
FAUX en l'état actuel — le dashboard Flutter a une vraie section financière
(ci-dessus). Ce qui est vrai : ni le dashboard web ni le dashboard Flutter
n'affichent de KPI "Ventes impayées/Montant impayé" — c'est voulu et
symétrique (guide.txt section 2, déjà fait des deux côtés). Le tableau
"Ventes à crédit" détaillé (par client) existe uniquement sur /reports (web),
voir §10 — c'est ÇA qui manque en Flutter, pas un KPI de dashboard.

CE QUE LE WEB A QUE FLUTTER N'A PAS :
  - Graphe "Stock par catégorie" (camembert/barres).
  - Liste "Ventes récentes" (8 dernières transactions nommées, avec vendeur/
    magasin) — Flutter n'a que des compteurs agrégés (Stock rapide), pas de
    liste d'items individuels récents.
  - Liste "Alertes de stock" avec NOMS de produits (jusqu'à 8) — Flutter
    "Stock rapide" ne donne que des compteurs (ruptures/stock bas), pas les
    noms (il faut aller dans Produits → onglet Ruptures pour les noms, ce
    qui existe donc ailleurs, pas un vrai manque).
  - KPI "Admins/Magasins" (effectif) — mineur.

TROUVAILLE ANNEXE (bug indépendant, pas un écart web/Flutter) : le modèle
Flutter DashboardFinance attend un champ total_pub_meta_ads (models/
dashboard.dart:41,49) mais orders/dashboard.py ne renvoie JAMAIS ce champ
dans analyse_financiere (dashboard.py:172-177) — il n'entre même pas dans le
calcul de benefice_estime (dashboard.py:91, somme seulement prix_fournisseur+
fret_import+douane). Résultat : la ligne "Total pub Meta Ads" du dashboard
Flutter affichera toujours 0 Ar. Se recoupe avec le §16 (suppliers) — voir
là-bas pour la cause complète.

VERDICT : PAS UN GAP AU SENS "Flutter en retard" — c'est un dashboard
parallèle, différent, et sur plusieurs points (analyse financière, période,
TOP produits multi-dimension) plus riche que le web. Les manques réels sont
mineurs (liste nominative des ventes récentes, stock par catégorie). Corriger
le mental model : le dashboard Flutter n'est pas "en retard", il a
simplement évolué séparément avec son propre endpoint.

de cette page est probablement déjà cassée CÔTÉ WEB LUI-MÊME, indépendamment
de Flutter : reports.tsx charge ses données via djangoClient.sales.list()
(frontend/lib/django-client.ts:820-844), qui est un SHIM DE COMPATIBILITÉ
(pas un vrai modèle "Sale" en base — aucune classe Sale trouvée dans
*/models.py) dérivé des commandes LIVRE, avec `total_profit: 0` codé en dur
(ligne 837) et sans champ `payment_amount` du tout. Conséquence en suivant
le calcul (reports/page.tsx:57-68) :
  - "Bénéfice net" (KPI) et les colonnes "Bénéfice" des tableaux Top
    produits/Top vendeurs/Top magasins semblent toujours valoir 0 Ar (somme
    d'une valeur codée en dur à 0).
  - Le tableau "Ventes à crédit" semble lister TOUTES les lignes de
    commande livrées avec un solde dû égal au prix plein (la condition
    `payment_amount < total_price` est toujours vraie puisque
    payment_amount est toujours undefined→0), pas seulement les vraies
    ventes à crédit.
  - Seule l'IA (aiData.beneficeNet, ligne 178) contourne le problème en
    préférant dashboardKpis.total_profit (le vrai calcul, venant de /users/
    dashboard/) — donc l'analyse IA elle-même reste correcte, mais pas
    l'affichage direct de la page.
Ceci est une lecture statique du code, pas une vérification à l'exécution —
à confirmer en conditions réelles avant de conclure définitivement, mais le
chemin logique est clair et mérite une vérification rapide côté web AVANT
d'investir dans un portage Flutter de ces deux éléments précis (bénéfice net
affiché, ventes à crédit) — le graphe CA, le Top produits (quantités, ça
c'est fiable), la répartition mouvements et l'IA restent eux pleinement
valables et sont le vrai coeur du gap.

VERDICT : GAP RÉEL, LE PLUS IMPORTANT DE L'AUDIT. Confirme l'hypothèse de
l'utilisateur (plus gros qu'un simple oubli de 2 KPI) — mais avant de porter
tel quel, vérifier/corriger le calcul "bénéfice"/"ventes à crédit" côté web,
sinon on porterait un bug vers le mobile.
